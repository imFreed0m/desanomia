# 18 Decisions

Log every design choice. Status: Accepted (authoritative, verified against project invariants), Proposed (drafted in `brain/`, awaiting hardware validation), Open (needs an answer). Do not change an Accepted decision without explicit justification and updating affected files.

## Accepted

- **D-001 (Dosing Architecture):** Semi-closed loop dosing. Initial open-loop feedforward dose based on calibrated volume-to-time formula ($V_{mL} \times 0.107\text{ s/mL}$). If mean TDS < 1200 ppm after mixing (120 s) and settling (15 s), execute exactly one single-pass top-up recovery (capped at 300 mL max). If still outside 1200–1300 ppm or if initial TDS > 1300 ppm, latch `FAULT_PPM_OUT_OF_RANGE` and lock distribution pump OFF. Reason: Eliminates chemical hunting and overdosing risk while recovering minor concentration deficits.
- **D-002 (Target TDS & Gate Band):** Target TDS is 1250 ppm with an inclusive gate band of 1200 to 1300 ppm for a 140.0 L batch in Distribution Drum (Drum 2). (Supersedes earlier 600 ppm recipe draft). Reason: Grounded in greenhouse field test standards and `DOSE_TEST_RESULT.md`.
- **D-003 (Safety Interlocks):** Seven firmware-enforced safety interlocks locally on ESP32 (TDS Gate, Dry-Run Cutoff, Batch Depletion, Dual-Stage Fill Guard, Water Baseline & Plausibility, Radar Liveness Watchdog, Emergency Stop Guard). Zero bypass in AUTO or MANUAL mode. Reason: Hardware safety must not depend on network, backend, or UI availability.
- **D-004 (Distribution Topology):** Single distribution pump feeding all 6 beds (B1–B6, 980 dripper points) simultaneously; no per-zone solenoid valves or manifold switching in Phase 1. Reason: Hydraulic stability, pressure consistency, and simplified mechanical failure envelope.
- **D-005 (Edge Platform & Technology Stack):** Edge host is an on-site Beelink EQ12 Mini PC (Intel N100) running Docker Compose: FastAPI backend (Python 3.12, async, aiomqtt, WebSockets), PostgreSQL (SQLAlchemy 2.0 + Alembic), Eclipse Mosquitto MQTT broker, and React + Vite + TypeScript dashboard served as an offline static bundle via Nginx. Microcontroller is ESP32-S3 N16R8 with FreeRTOS. (Onlook, Next.js, and PocketBase are explicitly discarded).
- **D-006 (Authentication & Roles):** Session-based username and password authentication with roles: Admin, Operator, Viewer.
- **D-007 (Network Topology & Remote Access):** Local greenhouse LAN for operations; remote operator access via Tailscale mesh VPN. Operational alerts are dispatched via Telegram Bot as an outbound alerting channel featuring secure inline action buttons on critical event messages (`[Siram Sekarang]`, `[Tunda 1 Jam]`, `[Konfirmasi Pause Recovery]`) for 1-tap remote authorization without raw free-text terminal commands.
- **D-008 (Scope & Non-Goals):** Phase 1 scope is strictly limited to automated batch fertigation. Non-goals (environmental sensors, plant tracking, native mobile apps, AI predictive dosing) remain strictly unbuilt.
- **D-013 (Mid-Batch Power Outage & Dynamic Deficit Dosing):** On mid-batch power recovery with Drum 2 level > 5.0 L, the system initializes safely into un-energized `BATCH_PAUSED_INSPECTION` mode. The UI presents an intrusive screen-locking modal displaying real-time volume, measured PPM, and dynamically calculated deficit concentrate (mL) required to reach target recipe PPM. Operator can inspect and confirm continuation, or the system auto-resumes after 30 minutes if all 7 firmware safety interlocks pass. Manual gravity drain to ≤ 5.0 L is mandated only during catastrophic spikes (> 500 ppm above target) or physical plumbing leaks.
- **D-014 (Offline-First Greenhouse Panel Core vs Display Tiers):** Core greenhouse batch fertigation, safety interlocks, and Primary HMI Touchscreen (UPERFECT BE156PF 15.6" IPS FHD on 90 cm standing kiosk) run 100% offline directly on the Beelink EQ12 Mini PC + ESP32 via HDMI/USB-C and never halt due to internet loss. The Secondary Display in the Gazebo (Xiaomi TV A 43" FHD 2026 running Fully Kiosk Browser 24/7 over wired LAN / Gazebo DMZ) serves as a passive read-only mirror. Remote mobile web (smartphones) displays last known state with an offline indicator during internet drops and hydrates a complete telemetry snapshot in < 500 ms upon reconnection.
- **D-019 (Emergency Stop UI/UX & Live Hardware Switch Sensing):** Dual E-stop design: instant 1-tap button (min 56 × 56 px) on local kiosk touchscreen; confirmation modal (`aria-modal="true"`) on remote web clients to prevent accidental triggers. The physical mushroom button is wired via hardwired NC contact to an ESP32 GPIO interrupt pin. ESP32 continuously reports `hw_estop_pressed` boolean telemetry. While contacts remain physically open/latched, the UI `Reset Fault` button is locked with 'Tombol E-Stop Fisik Masih Tertekan — Putar untuk Melepas'. Unlocks only when contacts close and Drum 2 level ≤ 5.0 L.
- **D-022 (Concentrate Stock Level & Starvation Detection):** Concentrate Drum (Drum 1) has no hardware level sensor. Stock depletion is detected inferentially based on empirical dosing calibration (`DOSE_TEST_RESULT.md`): if post-dosing TDS exhibits a significant negative anomaly (e.g. measuring ~1000 ppm instead of expected ~1250 ppm), the system flags an immediate warning/alert for operator inspection to check if Drum 1 is dry/starved.
- **D-024 (Batch Scheduling Execution & Overlap Arbitration):** Scheduled batches execute unattended without requiring operator presence, strictly guarded by the 7 autonomous firmware safety interlocks (Drum 2 empty ≤ 5.0 L, baseline water valid, no latched faults, ESP32 online). If a manual batch is initiated while a schedule is imminent (< 15 min), UI prompts an explicit postponement warning. If an automated schedule triggers while a manual batch is running or during Pause Mode, the scheduler defers execution until Drum 2 ≤ 5.0 L (canceling with a Telegram alert if the deferral window exceeds 60 minutes to prevent over-irrigation).
- **D-025 (Minimalist In-App Notification Hub & 5W1H Operational Alert Matrix):** In-app alerts are delivered via an Apple-inspired minimalist glassmorphic interface: (1) Persistent Header Notification Center with unread counter, (2) Slide-out Frosted Glass Notification Drawer with categorized history, (3) Floating Interactive Toasts with 1-tap action buttons (`[Lihat Detail]`, `[Konfirmasi Refill]`, `[Kuras Drum]`), and (4) 4-tier severity model (Critical, Warning, Success, Info) with selective subtle UI audio chimes on the HMI Kiosk (gentle glass ping for warnings, double chime for critical faults/E-stop; completely silent for routine success and info). Outbound Telegram bot with interactive inline callback buttons operates concurrently for remote notifications. Replenishment of Concentrate Drum (Drum 1) continues to enforce the mandatory Refill Confirmation Gate resetting virtual stock to 20.0 L.
- **D-034 (Drum Nomenclature):** Standardized English canonical terms: **Concentrate Drum (Drum 1)** for the 20 L fertilizer stock container, and **Distribution Drum (Drum 2)** for the 140 L mixing and irrigation tank. UI labels use clear Indonesian equivalents.
- **D-035 (Single Source of Truth):** `brain/` is the sole authoritative repository for project requirements, architecture, and specifications. Documents under `docs/` serve as historical reference inputs and are progressively aligned into `brain/`.
- **D-036 (Guided Sensor Calibration & Water Baseline Offset):** Analog TDS probe maintenance requires a dedicated step-by-step calibration wizard on `/manual`. Because the probe is plumbed directly into the distribution tank (side/bottom), the wizard strictly enforces that Drum 2 is drained (≤ 5.0 L) and FSM is IDLE before the operator is guided to detach it. Calibration uses a standard 1413 µS/cm reference buffer with a 30s ADC stabilization window and explicitly factors in the greenhouse raw water baseline PPM offset. Calibrated slope/offset are committed directly to ESP32 NVS with immutable backend audit logging (`SENSOR_CALIBRATED`).
- **D-037 (Named Recipe Presets Library & Agricultural Traceability):** The system manages fertigation targets via a dedicated Named Recipe Presets Library on `/recipes` (e.g. Vegetatif: 1100 ppm, Generatif: 1250 ppm, Panen: 1050 ppm). Operators can add, modify default targets, or archive presets. The active preset persists across manual and scheduled runs. Every batch run permanently snapshots the recipe preset name and target band into PostgreSQL, ensuring historical agricultural auditability on `/batches/:id`.
- **D-038 (Unified Schedule-First Pipeline & Dynamic Baseline Reference):** All automated execution originates strictly from manual operator configuration. To eliminate split-brain logic between automated schedules and manual runs, every execution is managed by a single unified scheduling engine. An ad-hoc operator run is registered as an immediate batch (`schedule_at = NOW`). If an ad-hoc batch is executed earlier than a planned schedule on that day (e.g. 10:00 vs 11:00), the later schedule is automatically deleted/suppressed to prevent duplicate irrigation, and the 10:00 execution timestamp dynamically becomes the new baseline reference for the subsequent autonomous recurrence interval.
- **D-039 (Same-Day Double Distribution Protection & Hard Confirmation Gate):** Crops must be protected from accidental or uncoordinated over-fertigation. Once a successful distribution occurs on any calendar day, initiating an additional distribution on that day is interlocked by default. Overriding this lockout requires a high-friction Hard Confirmation Modal with explicit hazard warnings (root asphyxiation and EC salinity toxicity), logging `SAME_DAY_FORCE_OVERRIDE` to the immutable audit trail.
- **D-040 (Multi-Tank 5-Pair Architecture & Dashboard Zero-Conflict Calendar):** The system architecture accommodates 5 pairs of tanks: 5 Concentrate Drums (K1–K5, 20 L each) and 5 Distribution Drums (D1–D5, 140 L each). In Phase 1, Pair 1 (Concentrate Drum 1 and Distribution Drum 2 in physical nomenclature) is actively plumbed; Pairs 2–5 are displayed on the Dashboard with 'Standby / Belum Terpasang' badges. Because all distribution drums share a single high-pressure distribution pump and mainline manifold, no two distribution tanks may distribute on the same day or overlapping time window (Zero Conflict Invariant). The Dashboard features an integrated Calendar and Timeline widget to schedule, arbitrate, and visualize non-conflicting allocations.
- **D-041 (Single Upfront Batch Confirmation & Autonomous Distribution):** Batch creation consolidates Recipe Selection, Timing ('Now' vs 'Later'), and Tank Pair selection into a single upfront modal. Once confirmed and preparation steps (Fill -> Dose -> Mix -> Stabilize -> Measure TDS) pass the TDS safety gate, the system transitions to `DISTRIBUTING` 100% autonomously without requiring a secondary manual confirmation step.
- **D-042 (Dual Visual Hierarchy for 12 FSM States & Dynamic Fluid Surface Physics):** Every state across the 12 FSM lifecycle states is rendered with distinct visual clarity across two synchronized layers: (1) an Apple-style minimalist horizontal Pipeline Stepper bar mounted directly above the active tank card (showing active node, completed milestones, and live timers), and (2) dynamic modular fluid surface physics within the SVG/Canvas drum visualizer (rising wave for FILLING, rotational vortex swirl for MIXING, glassy calm for STABILIZING, neon probe glow for MEASURING, draining wave for DISTRIBUTING, red hazard pulse for FAULT, and amber deficit wave for PAUSED_INSPECTION).

- **D-020 (Time Synchronization & Offline Chrony NTP Master):** Beelink EQ12 uses its onboard CR2032 battery-backed motherboard RTC (`/dev/rtc0`) as the authoritative local time master on boot (`hwclock --hctsys`). The Beelink runs `chrony` configured as a local stratum-10 NTP server on the isolated OT LAN (`192.168.10.1:123`). The ESP32-S3 FreeRTOS firmware syncs its internal clock via standard SNTP every 60 minutes over LAN. When the 4G WAN uplink (Orbit Star H2) is connected, chrony synchronizes with public NTP pools (`pool.ntp.org`) and updates the motherboard RTC (`hwclock --systohc`). Eliminates extra hardware RTC modules while ensuring drift-free unattended fertigation schedules.
- **D-026 (Tier-Differentiated Auth Session Lifespan):** Session lifespans are strictly differentiated across client tiers:
  1. *Primary HMI Touchscreen Kiosk:* Persistent local loopback `Operator` session with zero idle lockout, allowing instant operational and emergency control without login barriers. Administrative actions require step-up authentication.
  2. *Secondary Gazebo Display (Xiaomi TV 43"):* Auto-authenticated `Viewer` session via Nginx client IP allowlist (`192.168.1.50`) and read-only device bearer token, strictly blocking mutation endpoints at the reverse proxy.
  3. *Remote Mobile Clients / PWA:* Enforce a sliding 8-hour idle timeout and 7-day absolute maximum lifetime with secure HTTP-only cookies.
  All sessions are backed by PostgreSQL tokens for instant administrative revocation.
- **D-027 (Phase 1 Firmware Security & Non-Destructive Flashing):** In Phase 1 development and greenhouse trials, ESP32-S3 physical eFuses remain unburned (no one-way permanent hardware Flash Encryption or Secure Boot v2 burning). This allows rapid iterative PlatformIO flashing and UART/JTAG debugging. Transport security is enforced via network isolation (OT LAN) and MQTT username/password credentials with topic ACLs. Irreversible hardware flash encryption, Secure Boot v2 (RSA-3072), and signed HTTPS OTA updates are scheduled for Phase 2 production lockdown.
- **D-043 (Network Interface Segmentation & MQTT Isolation):** Beelink EQ12 leverages its Dual 2.5 GbE NICs: ETH0 (192.168.10.1) dedicated to OT Industrial LAN for ESP32-S3; ETH1 (192.168.1.10) dedicated to IT/WAN Uplink (Orbit Star H2, Tenda O1 Gazebo PTP bridge, Tailscale). Eclipse Mosquitto binds strictly to ETH0:1883 with `allow_anonymous false` and topic ACLs. Host IP forwarding is disabled.
- **D-044 (Telemetry Persistence, Partition Retention & Dual Backup):** PostgreSQL 16 employs native monthly range partitioning for raw telemetry. FastAPI buffers readings in RAM with 5-second asynchronous bulk inserts to minimize NVMe write IOPS. Drops occur per complete monthly partition (effective retention 90–120 days) after verifying 1-minute rollups are complete. Backups enforce a dual-target strategy: daily local compressed `pg_dump` on NVMe (retaining 30 days) plus secondary off-device copy via mounted external USB/SATA drive and rsync over Tailscale.
- **D-045 (Command Idempotency & NVS Boot Recovery):** MQTT commands carry a UUID `cmd_id` over QoS 1. The ESP32 tracks the last 32 executed IDs in a circular RAM cache and persists `last_executed_cmd_id` to NVS flash, preventing duplicate execution of retransmitted QoS 1 commands upon microcontroller reboot.

## Proposed

- **D-010 (FSM Execution Authority):** FSM executes autonomously on ESP32 firmware; backend mirrors state via MQTT telemetry. Reason: Batch execution survives edge server reboot or network dropouts.
- **D-011 (Fault Representation):** Fault is a latched status flag accompanied by dedicated fault codes, not a destructive state wipe. FSM requires explicit manual or gated reset.
- **D-012 (Gate Failure Outcome):** Gate failure locks distribution pump OFF, halts batch progress, and alerts operator. Recovery requires manual gravity drain to <= 5.0 L before reset is unlocked.
- **D-015 (Command Idempotency):** Actuator and state-changing commands include unique `cmd_id` and are acknowledged via MQTT ack topics.
- **D-016 (Telemetry Retention):** Raw high-frequency telemetry stored for 90 days in PostgreSQL, rolled up into 1-minute aggregates for long-term historical analytics.
- **D-017 (MQTT Topic Hierarchy):** Standardized MQTT topic namespace under `desanomia/gh1/`.
- **D-018 (Firmware Tooling):** PlatformIO for ESP32 firmware development, C++ with FreeRTOS tasks.
- **D-019 (Emergency Stop UI/UX & Live Hardware Switch Sensing):** Dual E-stop design: instant 1-tap button (min 56 × 56 px) on local kiosk touchscreen; confirmation modal (`aria-modal="true"`) on remote web clients to prevent accidental triggers. The physical mushroom button is wired via hardwired NC contact to an ESP32 GPIO interrupt pin. ESP32 continuously reports `hw_estop_pressed` boolean telemetry. While contacts remain physically open/latched, the UI `Reset Fault` button is locked with 'Tombol E-Stop Fisik Masih Tertekan — Putar untuk Melepas'. Unlocks only when contacts close and Drum 2 level ≤ 5.0 L.
- **D-028 (User Provisioning):** Admin creates accounts; initial admin seeded via backend CLI with forced initial password reset.
- **D-029 (UI Theme & Aesthetics):** Industrial cockpit theme optimized for greenhouse control room lighting (high contrast, tabular figures, no heavy animation or particle slop).
- **D-030 (Manual Actuator Gating):** Manual actuator testing controls are disabled during active batch FSM execution.

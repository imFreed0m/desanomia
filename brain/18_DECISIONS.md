# 18 Decisions

Central Architectural Decision Records (ADR) for the DESANOMIA precision greenhouse automated fertigation and edge monitoring system.

**Status Taxonomy:**
- **Accepted:** Authoritative architectural invariant verified against project requirements, master rules (`brain/00_MASTER_RULES.md`), and hardware safety constraints.
- **Proposed:** Drafted in `brain/`, awaiting physical greenhouse trial validation.
- **Open:** Under investigation with unresolved technical tradeoffs.

---

## Accepted Decisions (D-001 through D-046)

- **D-001 (Dosing Architecture):** Semi-closed loop dosing. Initial open-loop feedforward dose based on calibrated volume-to-time formula ($V_{\text{mL}} \times 0.107\text{ s/mL}$). After mixing (120 s) and settling (15 s): (a) if mean TDS is in $[\text{Target} - 250\text{ ppm},\ \text{Target} - 50\text{ ppm})$, execute exactly one single-pass top-up recovery (capped at 300 mL max); (b) if mean TDS $< (\text{Target} - 250\text{ ppm})$, raise `STARVATION_SUSPECTED` (likely empty Drum 1) and skip top-up; (c) if after top-up or on initial evaluation TDS remains outside $[\text{Target} - 50\text{ ppm},\ \text{Target} + 50\text{ ppm}]$, or if initial TDS $> (\text{Target} + 50\text{ ppm})$, latch `FAULT_PPM_OUT_OF_RANGE` and lock distribution pump OFF. Reason: Eliminates chemical hunting and overdosing risk while recovering minor concentration deficits and detecting dry-drum starvation.

- **D-002 (Target TDS & Dynamic Gate Band):** Default Target TDS is 1250 ppm (Generatif recipe) with an inclusive dynamic gate band of $[\text{Target} - 50\text{ ppm},\ \text{Target} + 50\text{ ppm}]$ (1200 to 1300 ppm for Generatif; 1050–1150 ppm for Vegetatif; 1000–1100 ppm for Panen) for a 140.0 L batch in Distribution Drum (Drum 2). Supersedes earlier static 600 ppm single-target draft. Reason: Grounded in commercial greenhouse crop growth stages, standard agronomic requirements, and empirical field calibration (`DOSE_TEST_RESULT.md`).

- **D-003 (Safety Interlocks Authority):** Seven firmware-enforced safety interlocks locally on ESP32 (`IL-01` TDS Gate, `IL-02` Dry-Run Cutoff, `IL-03` Batch Depletion Guard, `IL-04` Dual-Stage Fill Timeout, `IL-05` Water Baseline & Plausibility Guard, `IL-06` FMCW Radar Liveness Watchdog, `IL-07` Physical Emergency Stop Guard). Zero bypass permitted in AUTO or MANUAL mode. Reason: Hardware safety must operate with absolute autonomy and zero dependency on edge server, network switch, or UI availability.

- **D-004 (Distribution Topology):** Single 0.5 HP distribution pump feeding all 6 elevated cultivation beds (B1–B6, 980 dripper points total) simultaneously; no per-zone solenoid valves or manifold switching in Phase 1. Reason: Hydraulic pressure stability, uniform emitter flow across beds, and minimization of mechanical failure points.

- **D-005 (Edge Platform & Technology Stack):** Edge host is an on-site Beelink EQ12 Mini PC (Intel N100, 16GB DDR5, 500GB NVMe) running Debian 12 Minimal with Docker Compose: FastAPI backend (Python 3.12, async, aiomqtt, WebSockets), PostgreSQL 16 (SQLAlchemy 2.0 + Alembic, monthly range partitions), Eclipse Mosquitto 2.0 MQTT broker, and React 18/19 + Vite + TypeScript dashboard served as an offline static bundle via Nginx. Microcontroller is ESP32-S3 N16R8 (16MB Flash, 8MB Octal PSRAM) running FreeRTOS with PlatformIO. (Onlook, Next.js, and PocketBase are explicitly discarded).

- **D-006 (Authentication & Roles):** Session-based username and password authentication with three strictly segregated roles: Admin (system configuration, user provisioning, calibration, manual overrides), Operator (batch initiation, schedule modification, fault reset), and Viewer (passive real-time monitoring and historical telemetry review).

- **D-007 (Network Topology & Remote Access / Outbound Telegram Bot):** Local greenhouse LAN for primary operations; secure remote administrative access via Tailscale mesh VPN. Operational alerts and warnings are dispatched via Telegram Bot as an outbound alerting channel featuring secure inline action buttons on critical event messages (`[Siram Sekarang]`, `[Tunda 1 Jam]`, `[Konfirmasi Pause Recovery]`) for 1-tap remote authorization without requiring raw terminal commands.

- **D-008 (Scope & Non-Goals):** Phase 1 scope is strictly limited to automated batch fertigation, safety interlocks, edge telemetry persistence, and multi-tier operator interfaces. Non-goals (microclimate HVAC integration, soil moisture sensors, computer vision plant monitoring, native mobile store apps, and AI predictive dosing) remain strictly unbuilt.

- **D-009 (Hardware Fail-Safe Relay De-Energization):** All actuator power relays (fill solenoid, peristaltic dosing pump, submersible mixer, distribution pump) are active-LOW optoisolated relays wired exclusively to Normally Open (NO) power contacts. On microcontroller reset, brownout, panic, or power severance, GPIO pins float to high-impedance (pulled HIGH) or lose 5V VCC, forcing immediate 0 ms mechanical relay de-energization. Reason: Fail-safe physical invariant preventing uncommanded flooding or chemical overdose.

- **D-010 (FSM Execution Authority):** The 12-state fertigation Finite State Machine executes autonomously on bare-metal ESP32 FreeRTOS firmware (pinned to Core 1 at 20 Hz). The FastAPI edge backend mirrors state via MQTT telemetry. Reason: Batch execution survives edge host reboot, Docker container restart, or fieldbus network dropouts without leaving valves open or pumps running unattended.

- **D-011 (Latched Fault Representation & Zero State Wipe):** Faults are treated as latched status flags accompanied by dedicated fault codes (`FAULT_*`), not destructive state wipes or ad-hoc FSM resets. When a safety interlock trips, the FSM transitions into a safe halted state with all relays de-energized, persisting the exact failure context and requiring an explicit gated clearance before resuming normal operations.

- **D-012 (Gate Failure Outcome & Gated Reset Precondition):** If post-mix TDS fails the quality gate band, the distribution pump is locked OFF, batch progress is halted, local alarms trigger, and an alert is dispatched. Resetting the fault is interlocked: the operator must manually drain the off-spec solution via the bottom gravity drain valve until Distribution Drum (Drum 2) volume is $\le 5.0\text{ L}$ before the firmware permits de-latching. Reason: Prevents pumping toxic or improperly mixed solution to crops.

- **D-013 (Mid-Batch Power Outage & Dynamic Deficit Dosing):** On mid-batch power recovery with Drum 2 level $> 5.0\text{ L}$, the system initializes safely into un-energized `BATCH_PAUSED_INSPECTION` mode. The UI presents an intrusive screen-locking modal displaying real-time volume, measured PPM, and dynamically calculated deficit concentrate (mL) required to reach target recipe PPM. Operator can inspect and confirm continuation, or the system auto-resumes after 30 minutes if all 7 firmware safety interlocks pass. Manual gravity drain to $\le 5.0\text{ L}$ is mandated only during catastrophic spikes ($> 500\text{ ppm}$ above target) or physical plumbing leaks.

- **D-014 (Offline-First Greenhouse Panel Core vs Display Tiers):** Core greenhouse batch fertigation, safety interlocks, and Primary HMI Touchscreen (UPERFECT BE156PF 15.6" IPS FHD on 90 cm standing kiosk) run 100% offline directly on the Beelink EQ12 Mini PC + ESP32 via HDMI/USB-C loopback (`127.0.0.1:8080`) and never halt due to internet loss. The Secondary Display in the Gazebo (Xiaomi TV A 43" FHD 2026 running Fully Kiosk Browser 24/7 over wired LAN / Gazebo DMZ `192.168.1.50`) serves as a passive read-only mirror. Remote mobile web (smartphones over Tailscale) displays last known state with an offline indicator during internet drops and hydrates a complete telemetry snapshot in $< 500\text{ ms}$ upon reconnection.

- **D-015 (Command Idempotency Envelope):** All actuator commands and state-changing requests must carry a unique UUID `cmd_id` transmitted over MQTT QoS 1. The receiver acknowledges commands on dedicated ACK topics with execution status (`ACCEPTED`, `REJECTED`, `ALREADY_EXECUTED`). Commands with duplicate IDs within the execution window are acknowledged without re-triggering physical hardware.

- **D-016 (Telemetry Retention & Aggregation):** Raw high-frequency (1.0 Hz / 5-second buffered) telemetry is stored in PostgreSQL native monthly range partitions with an effective retention period of 90–120 days. High-frequency data is continuously aggregated into 1-minute statistical rollups (`telemetry_1m`), which are retained for 2 years for long-term agronomic analytics and seasonal crop comparison.

- **D-017 (MQTT Topic Hierarchy):** Standardized MQTT topic tree under the root namespace `desanomia/gh1/`: `cmd` for edge commands, `ack` for correlated execution receipts, `telemetry` for consolidated 1.0 Hz sensor metrics, `events` for FSM state transitions and interlock trips, `lwt` for hardware connection liveness supervision, and `heartbeat` for 10-second firmware health reporting.

- **D-018 (Firmware Tooling & Development Framework):** ESP32-S3 firmware is developed using PlatformIO with the ESP-IDF framework (using C++17/C++20). Real-time safety loops, task scheduling, queues, and semaphores are built using FreeRTOS primitives with strict compile-time static allocation (`xTaskCreateStaticPinnedToCore`).

- **D-019 (Emergency Stop UI/UX & Live Hardware Switch Sensing):** Dual E-stop architecture: instant 1-tap software button (min $56 \times 56\text{ px}$) on local kiosk touchscreen; confirmation modal (`aria-modal="true"`) on remote web clients to prevent accidental network triggers. The physical mushroom button is wired via a hardwired NC contact in series with relay coil power (0 ms mechanical cut) and tapped to ESP32 GPIO 21 interrupt. ESP32 continuously reports `hw_estop_pressed` boolean telemetry. While contacts remain physically open/latched, the UI `Reset Fault` button is locked with 'Tombol E-Stop Fisik Masih Tertekan — Putar untuk Melepas'. Unlocks only when contacts close and Drum 2 level $\le 5.0\text{ L}$.

- **D-020 (Time Synchronization & Offline Chrony NTP Master):** Beelink EQ12 uses its onboard CR2032 battery-backed motherboard RTC (`/dev/rtc0`) as the authoritative local time master on boot (`hwclock --hctosys`). The Beelink runs `chrony` configured as a local Stratum-10 NTP server on the isolated OT LAN (`192.168.10.1:123`). The ESP32-S3 FreeRTOS firmware syncs its internal clock via standard SNTP every 60 minutes over LAN. When the 4G WAN uplink (Orbit Star H2) is connected, chrony synchronizes with public NTP pools (`pool.ntp.org`) and updates the motherboard RTC (`hwclock --systohc`). Eliminates extra hardware RTC breakout boards while ensuring drift-free unattended fertigation schedules.

- **D-021 (Bilingual Terminology & UI Language Strategy):** UI labels, operational prompts, buttons, dialogs, and audible alarms are formatted in Bahasa Indonesia for immediate clarity to local greenhouse farmhands and greenhouse operators. Technical specifications, system architecture, database schemas, API models, log events, and codebase comments are authored in English.

- **D-022 (Concentrate Stock Level & Starvation Detection):** Concentrate Drum (Drum 1) has no hardware electronic level sensor. Stock volume is tracked inferentially in PostgreSQL `concentrate_stock` (20.0 L initial capacity, decremented per batch by $V_{\text{dose}} + V_{\text{topup}}$, warning at $\le 3000\text{ mL}$). Depletion starvation is detected inferentially based on empirical dosing calibration (`DOSE_TEST_RESULT.md`): if post-dosing TDS exhibits a significant negative anomaly ($> 250\text{ ppm}$ deficit below target), the system flags an immediate `STARVATION_SUSPECTED` warning for operator inspection. Replenishing Drum 1 requires acknowledging the Refill Confirmation Gate.

- **D-023 (Gate Inclusivity & Strict Quality Boundary):** The TDS gate condition is evaluated as an inclusive numeric range $[\text{Target} - 50\text{ ppm},\ \text{Target} + 50\text{ ppm}]$. Values at exactly $\text{Target} - 50\text{ ppm}$ or $\text{Target} + 50\text{ ppm}$ are considered valid passes. Any value outside this closed interval triggers top-up recovery (if within deficit reach) or latches `FAULT_PPM_OUT_OF_RANGE`.

- **D-024 (Batch Scheduling Execution & Overlap Arbitration):** Scheduled batches execute unattended without requiring operator presence, strictly guarded by the 7 autonomous firmware safety interlocks (Drum 2 empty $\le 5.0\text{ L}$, baseline water valid, no latched faults, ESP32 online). If a manual batch is initiated while a schedule is imminent ($< 15\text{ min}$), UI prompts an explicit postponement warning. If an automated schedule triggers while a manual batch is running or during Pause Mode, the scheduler defers execution until Drum 2 $\le 5.0\text{ L}$ (canceling with a Telegram alert if the deferral window exceeds 60 minutes to prevent over-irrigation).

- **D-025 (Minimalist In-App Notification Hub & 5W1H Operational Alert Matrix):** In-app alerts are delivered via an Apple-inspired minimalist glassmorphic interface: (1) Persistent Header Notification Center with unread counter, (2) Slide-out Frosted Glass Notification Drawer with categorized history, (3) Floating Interactive Toasts with 1-tap action buttons (`[Lihat Detail]`, `[Konfirmasi Refill]`, `[Kuras Drum]`), and (4) 4-tier severity model (Critical, Warning, Success, Info) with selective subtle UI audio chimes on the HMI Kiosk (gentle glass ping for warnings, double chime for critical faults/E-stop; completely silent for routine success and info). Outbound Telegram bot with interactive inline callback buttons operates concurrently for remote notifications. Replenishment of Concentrate Drum (Drum 1) continues to enforce the mandatory Refill Confirmation Gate resetting virtual stock to 20.0 L.

- **D-026 (Tier-Differentiated Auth Session Lifespan):** Session lifespans are strictly differentiated across client tiers:
  1. *Primary HMI Touchscreen Kiosk:* Persistent local loopback `Operator` session with zero idle lockout, allowing instant operational and emergency control without login barriers. Administrative actions require a 15-minute step-up elevation challenge.
  2. *Secondary Gazebo Display (Xiaomi TV 43"):* Auto-authenticated `Viewer` session via Nginx client IP allowlist (`192.168.1.50`) and read-only device bearer token, strictly blocking mutation endpoints at the reverse proxy.
  3. *Remote Mobile Clients / PWA:* Enforce a sliding 8-hour idle timeout and 7-day absolute maximum lifetime with secure HTTP-only cookies.
  All sessions are backed by PostgreSQL tokens for instant administrative revocation.

- **D-027 (Phase 1 Firmware Security & Non-Destructive Flashing):** In Phase 1 development and greenhouse trials, ESP32-S3 physical eFuses remain unburned (no one-way permanent hardware Flash Encryption or Secure Boot v2 burning). This allows rapid iterative PlatformIO flashing and UART/JTAG debugging. Transport security is enforced via network isolation (OT LAN) and MQTT username/password credentials with topic ACLs. Irreversible hardware flash encryption, Secure Boot v2 (RSA-3072), and signed HTTPS OTA updates are scheduled for Phase 2 production lockdown.

- **D-028 (User Provisioning & Administrative Bootstrapping):** User self-registration, public signup endpoints, and email verification workflows are strictly omitted. Administrative accounts are provisioned exclusively by existing Admins. The initial system administrator account is seeded during installation via backend CLI (`python -m app.cli.seed_admin`) with a mandatory forced password change upon first authentication.

- **D-029 (UI Theme & Aesthetics):** Industrial cockpit theme optimized for greenhouse control room lighting: deep dark background (`bg-slate-950`), high-contrast card borders (`border-slate-800`), tabular monospace numerals (`font-mono tabular-nums`), vibrant semantic semaphores (emerald for operational readiness, amber for inspection/hold, crimson for safety trip), and elimination of decorative particle animations, layout-shifting spinners, and AI visual clutter.

- **D-030 (Manual Actuator Gating & Operational Mutual Exclusion):** Manual actuator testing controls (jogging pumps, toggling valves) on `/manual` are strictly interlocked in both backend logic and ESP32 firmware whenever the FSM is in any state other than `IDLE`. Manual override commands sent during an active batch are rejected with `FSM_BUSY_CANNOT_MANUAL`.

- **D-031 (Modular Documentation Architecture):** User experience requirements and application flows (`02_APPFLOW.md`) and design tokens / styling briefs (`03_UI_UX_BRIEF.md`) are partitioned as standalone specification documents decoupled from the component implementation specification (`12_UI_SPEC.md`), enabling modular agent and developer context isolation.

- **D-032 (Brand Identity, Scientific Typography & Color Palette):** Visual hierarchy adopts the "Clean Laboratory Minimal" aesthetic stance: Space Grotesk for display headers and hero metrics, Geist Sans for operational body copy, and Geist Mono for high-frequency telemetry data. Palette uses perceptual OKLCH color spaces tailored for anti-glare readability in varied greenhouse ambient light.

- **D-033 (Sequential File Numbering & Development Lifecycle):** Specification files within `brain/` are organized in a 21-stage development progression: product definition (00–03), technical foundation and data contracts (04–07), cross-cutting cyber-physical rules (08–09), component implementation specifications (10–12), verification, release, and operations (13–16), execution roadmaps (17), decisions and logs (18–19), and canonical domain modeling (20).

- **D-034 (Drum Nomenclature):** Standardized English canonical terms: **Concentrate Drum (Drum 1)** for the 20 L fertilizer stock container, and **Distribution Drum (Drum 2)** for the 140 L mixing and irrigation tank. UI labels use clear Indonesian equivalents (*Drum 1 (Konsentrat)* and *Drum 2 (Distribusi)*).

- **D-035 (Single Source of Truth):** `brain/` is the sole authoritative repository for project requirements, architecture, and specifications. Documents under `docs/` serve as historical reference inputs and are progressively aligned into `brain/`.

- **D-036 (Guided Sensor Calibration & Water Baseline Offset):** Analog TDS probe maintenance requires a dedicated step-by-step calibration wizard on `/manual`. Because the probe is plumbed directly into the distribution tank (side/bottom), the wizard strictly enforces that Drum 2 is drained ($\le 5.0\text{ L}$) and FSM is IDLE before the operator is guided to detach it. Calibration uses a standard 1413 µS/cm reference buffer with a 30s ADC stabilization window and explicitly factors in the greenhouse raw water baseline PPM offset. Calibrated slope/offset are committed directly to ESP32 NVS with immutable backend audit logging (`SENSOR_CALIBRATED`).

- **D-037 (Named Recipe Presets Library & Agricultural Traceability):** The system manages fertigation targets via a dedicated Named Recipe Presets Library on `/recipes` (e.g. Vegetatif: 1100 ppm, Generatif: 1250 ppm, Panen: 1050 ppm). Operators can add, modify default targets, or archive presets. The active preset persists across manual and scheduled runs. Every batch run permanently snapshots the recipe preset name and target band into PostgreSQL, ensuring historical agricultural auditability on `/batches/:id`.

- **D-038 (Unified Schedule-First Pipeline & Dynamic Baseline Reference):** All automated execution originates strictly from manual operator configuration. To eliminate split-brain logic between automated schedules and manual runs, every execution is managed by a single unified scheduling engine. An ad-hoc operator run is registered as an immediate batch (`schedule_at = NOW`). If an ad-hoc batch is executed earlier than a planned schedule on that day (e.g. 10:00 vs 11:00), the later schedule is automatically deleted/suppressed to prevent duplicate irrigation, and the 10:00 execution timestamp dynamically becomes the new baseline reference for the subsequent autonomous recurrence interval.

- **D-039 (Same-Day Double Distribution Protection & Hard Confirmation Gate):** Crops must be protected from accidental or uncoordinated over-fertigation. Once a successful distribution occurs on any calendar day, initiating an additional distribution on that day is interlocked by default. Overriding this lockout requires a high-friction Hard Confirmation Modal with explicit hazard warnings (root asphyxiation and EC salinity toxicity), logging `SAME_DAY_FORCE_OVERRIDE` to the immutable audit trail.

- **D-040 (Multi-Tank 5-Pair Architecture & Dashboard Zero-Conflict Calendar):** The system architecture accommodates 5 pairs of tanks: 5 Concentrate Drums (K1–K5, 20 L each) and 5 Distribution Drums (D1–D5, 140 L each). In Phase 1, Pair 1 (Concentrate Drum 1 and Distribution Drum 2 in physical nomenclature) is actively plumbed; Pairs 2–5 are displayed on the Dashboard with 'Standby / Belum Terpasang' badges. Because all distribution drums share a single high-pressure distribution pump and mainline manifold, no two distribution tanks may distribute on the same day or overlapping time window (Zero Conflict Invariant). The Dashboard features an integrated Calendar and Timeline widget to schedule, arbitrate, and visualize non-conflicting allocations.

- **D-041 (Single Upfront Batch Confirmation & Autonomous Distribution):** Batch creation consolidates Recipe Selection, Timing ('Now' vs 'Later'), and Tank Pair selection into a single upfront modal. Once confirmed and preparation steps (Fill -> Dose -> Mix -> Stabilize -> Measure TDS) pass the TDS safety gate, the system transitions to `DISTRIBUTING` 100% autonomously without requiring a secondary manual confirmation step.

- **D-042 (Dual Visual Hierarchy for 12 FSM States & Dynamic Fluid Surface Physics):** Every state across the 12 FSM lifecycle states is rendered with distinct visual clarity across two synchronized layers: (1) an Apple-style minimalist horizontal Pipeline Stepper bar mounted directly above the active tank card (showing active node, completed milestones, and live timers), and (2) dynamic modular fluid surface physics within the SVG/Canvas drum visualizer (rising wave for FILLING, rotational vortex swirl for MIXING, glassy calm for STABILIZING, neon probe glow for MEASURING, draining wave for DISTRIBUTING, red hazard pulse for FAULT, and amber deficit wave for PAUSED_INSPECTION).

- **D-043 (Network Interface Segmentation & MQTT Isolation):** Beelink EQ12 leverages its Dual 2.5 GbE NICs: ETH0 (192.168.10.1) dedicated to OT Industrial LAN for ESP32-S3; ETH1 (192.168.1.10) dedicated to IT/WAN Uplink (Orbit Star H2, Tenda O1 Gazebo PTP bridge, Tailscale). Eclipse Mosquitto binds strictly to ETH0:1883 with `allow_anonymous false` and topic ACLs. Host IP forwarding is disabled (`net.ipv4.ip_forward = 0`).

- **D-044 (Telemetry Persistence, Partition Retention & Dual Backup):** PostgreSQL 16 employs native monthly range partitioning for raw telemetry. FastAPI buffers readings in RAM with 5-second asynchronous bulk inserts to minimize NVMe write IOPS. Drops occur per complete monthly partition (effective retention 90–120 days) after verifying 1-minute rollups are complete. Backups enforce a dual-target strategy: daily local compressed `pg_dump` on NVMe (retaining 30 days) plus secondary off-device copy via mounted external USB/SATA drive and rsync over Tailscale.

- **D-045 (Command Idempotency & NVS Boot Recovery):** MQTT commands carry a UUID `cmd_id` over QoS 1. The ESP32 tracks the last 32 executed IDs in a circular RAM cache and persists `last_executed_cmd_id` to NVS flash, preventing duplicate execution of retransmitted QoS 1 commands upon microcontroller reboot.

- **D-046 (Drum Visualization Rendering Technology):** Drum fluid visualization is rendered with SVG/HTML5 Canvas using optimized sine-curve wave physics at 60 FPS ($< 5\%$ CPU on Intel N100), as specified by TR-30 and D-042. React Three Fiber / WebGL / GLSL shaders and a 30 FPS cap are not used in Phase 1. Reason: Lower GPU/thermal load for 24/7 kiosk and TV operation, no WebGL dependency, simpler offline bundle.

- **D-047 (Multi-Tier Fault Taxonomy, Dosing Math Harmonization & Command Idempotency Reconciliation):**
  1. *Dosing Formula Calibration Constant:* Dynamic deficit concentrate volume formula in `09_ERROR_HANDLING.md`, `13_TESTING.md`, and `16_PRODUCTION_CHECKLIST.md` is strictly defined as $V_{\text{deficit\_mL}} = \frac{(\text{TDS}_{\text{target}} - \text{TDS}_{\text{measured}}) \times V_{\text{current\_L}}}{K_{\text{yield}}}$ where $K_{\text{yield}} = 107.0\text{ ppm}\cdot\text{L}/\text{mL}$. This yields exactly $196.26\text{ mL}$ for a $150\text{ ppm}$ deficit in $140.0\text{ L}$, and ensures the $300\text{ mL}$ maximum top-up cap safely covers up to a $229.3\text{ ppm}$ deficit, perfectly matching the $50–250\text{ ppm}$ top-up band mandated by `00_MASTER_RULES.md`.
  2. *Tier 1 Fault Subdivision:* Subdivides Tier 1 into 1A Latched Hardware Safety Faults (`IL-01`, `IL-02`, `IL-05`, `IL-06`, `IL-07` requiring manual drain to $\le 5.0\text{ L}$ + physical E-stop release + Gated Fault Reset), 1B Transient Command Precondition Rejections (`IL-03`: FSM stays in `IDLE`, MQTT ACK `REJECTED`, HTTP 409, no buzzer, no NVS latch), and 1C Resumable Hydraulic Pauses (`IL-04`: fill solenoid closed, buzzer OFF, recovered via `RESUME_FILL` without draining, capped at 3 resumes / cumulative 20 min).
  3. *Outage Recovery Ownership:* ESP32 FreeRTOS Core 1 owns the authoritative 30-minute safety timer and local deficit calculation (`fsm.CalculateDeficitDose`). Auto-resume executes strictly if all 7 interlocks pass, deficit $\le 300\text{ mL}$, and $\text{TDS} \le \text{Target} + 50\text{ ppm}$.
  4. *Command Timeout & Double Dosing Protection:* Upon 3.0 s command timeout, backend returns HTTP 504 `COMMAND_TIMEOUT` and the UI enters an `OUTCOME_UNKNOWN` reconciling state locking controls. Any operator retry must reuse the original `cmd_id`, ensuring ESP32's 32-slot circular RAM cache (`D-045`) suppresses duplicate physical actuation.
  5. *E-Stop Protection:* Software E-Stop is mounted outside `KioskErrorBoundary` (with fallback in crash view) and explicitly exempt from `STALE` and `OFFLINE` mutation lockouts, remaining 1-tap clickable 24/7.
  6. *Audit Log Synchronization:* Deprecates SHA-256 hash chaining columns across `06_DATA_MODEL.md`, `09_ERROR_HANDLING.md`, and `11_API_CONTRACT.md` in favor of PostgreSQL PL/pgSQL append-only triggers (`trg_audit_logs_immutability`) and daily offsite backup verification (`D-044`).

- **D-048 (Firmware Hardening, Volumetric Threshold Split, Fieldbus Autonomy & Hardware Failsafes):**
  1. *Volumetric Threshold Split & Debounce:* Resolves the 5.0 L formula floor race condition (`IL-02` vs normal exit vs `IL-03`). Normal distribution stops cleanly at $V \le 8.0\text{ L}$ (`BATCH_DEPLETED`). Dry-run safety cutoff `IL-02` trips at $< 6.0\text{ L}$ while the pump is active, debounced over 2 consecutive frames ($\le 200\text{ ms}$). Batch initiation and gated reset precondition permits start/reset at $\le 8.0\text{ L}$, eliminating spurious rejections from mm-scale radar jitter on an empty drum.
  2. *Hardware Dry-Run Backstop & Relay Failsafes:* Active-LOW relay inputs (GPIO 4–7) fit external 10 kΩ pull-ups to logic VCC so MCU reset/high-Z guarantees relays are OFF. `fsm_task`, `actuator_task`, and `sensor_task` subscribe to FreeRTOS Task Watchdog Timer (TWDT) with 3s panic reboot (`CONFIG_ESP_TASK_WDT_PANIC=y`). An independent mechanical NC float switch at 6.0 L height is wired in series with Relay 4 (distribution pump) AC power, providing a physical fail-safe dry-run cutoff.
  3. *Temperature-Compensated TDS (ATC):* Adds DS18B20 digital temperature sensor on GPIO 8 with 4.7 kΩ pull-up. The DFRobot Analog TDS probe conditioning formula incorporates the official cubic polynomial curve-fitting ($(133.42 V^3 - 255.86 V^2 + 857.39 V) \times 0.5 \times K_{\text{cell}}$) applied to temperature-compensated voltage ($V / (1 + 0.02(T - 25))$).
  4. *Fieldbus Comm-Loss Autonomy:* Resolves the contradiction in `08_SECURITY.md` §10.1 by choosing autonomy: on loss of Ethernet/MQTT, running batches finish under local ESP32 Core 1 safety interlocks, events spool to 8MB Octal PSRAM ring buffer, new batches are rejected, and the local pilot lamp blinks. The conflicting 10s automatic shutdown rule is deleted.
  5. *Command Replay Protection & 30s TTL:* ESP32 connects with `clean_session = true`. State-changing commands require $\text{now} - \text{timestamp} \le 30\text{ s}$ and synchronized SNTP clock (`ERROR_CLOCK_UNSYNCED`). `ESTOP`, `CANCEL`, and `RESET_FAULT` bypass TTL and clock sync.
  6. *Tiered E-Stop Recovery & Latched Watchdog Preconditions:* Relaxes mandatory tank draining in D-019 for intact E-stop interruptions: if solution was already mixed and tank is intact, operator on Kiosk may choose "Re-verify TDS & Resume" (`STABILIZING` $\to$ `MEASURING_TDS` $\to$ `GATE_EVALUATE`), or "Abort & Drain". `IL-06` radar watchdog latches on missing frames; cleared via `RESET_FAULT` once frames are stable for $\ge 3.0\text{ s}$ without dumping tank.
  7. *Task Architecture & Scoped Zero-Heap:* Task architecture pruned from 8 to 6 tasks (`fsm_task`, `actuator_task`, `sensor_task`, `w5500_driver_task`, `mqtt_task`, `psram_spooler_task`), delegating watchdog and time sync to native ESP-IDF `esp_task_wdt` and `esp_sntp`. Zero-heap rule scoped strictly to post-init recurring control loops. E-Stop ISR compiled into `IRAM_ATTR` with direct GPIO register write HIGH. PlatformIO build specifies 16MB flash, `sdkconfig.defaults`, `partitions_16mb.csv`, and dual OTA rollback cancellation (`esp_ota_mark_app_valid_cancel_rollback`).

- **D-049 (API Contract, Command Semantics & Wire Protocol Harmonization):**
  1. *Command Alignment & Endpoints:* Separates routine paused distribution resumption from outage recovery. `POST /batches/{id}/pause` dispatches `PAUSE_BATCH` (from `DISTRIBUTING`); `POST /batches/{id}/resume` dispatches `RESUME_BATCH` (from `PAUSED` back to `DISTRIBUTING`); dedicated `POST /batches/{id}/resume-deficit` dispatches `RESUME_DEFICIT_BATCH` with operator confirmation of calculated deficit dosing during `BATCH_PAUSED_INSPECTION` (`D-013`). `POST /faults/resume-fill` dispatches `RESUME_FILL` to clear `IL-04` timeouts without draining. `POST /batches/{id}/abort` dispatches `ABORT_BATCH` with immediate relay cut.
  2. *Safety Stop Precedence & Route Separation:* Relocates software E-stop to `POST /system/estop` and types `/actuators/{name}` strictly as `fill_valve`, `dosing_pump`, `mixing_pump`, `dist_pump`. For `ESTOP` and `ABORT_BATCH`, FastAPI publishes to MQTT `desanomia/gh1/cmd` immediately before recording the PostgreSQL `audit_logs` row asynchronously, guaranteeing slow DB queries never delay physical stop execution.
  3. *Idempotency & Polling Protocol:* Accepts client-supplied `Idempotency-Key` header (UUIDv4) as `cmd_id` (auto-generated if omitted). Adds `GET /api/v1/commands/{cmd_id}` for state reconciliation upon WebSocket drops. Defines `TIMEOUT` (3.0s) strictly as "Unknown, Check State" (never assumed failed; UI locks mutation retries to prevent duplicate jogs). Removes HTTP 504 from 202 async command flow; clarifies HTTP 409 `INTERLOCK_REJECTED` as a fast backend pre-check against cached telemetry before MQTT dispatch.
  4. *Safety Parameter & Calibration Hardening:* Removes `tolerance_band_ppm` across all API and MQTT schemas; firmware strictly hardcodes the ±50 ppm gate band constant (`IL-01`). ESP32 Core 1 autonomously re-validates numeric parameter bounds (target TDS 500–1800 ppm, manual actuator duration caps, calibration slope 0.5–2.0) rejecting invalid inputs with `PARAM_OUT_OF_BOUNDS`. TDS calibration endpoint accepts `buffer_ec_us_cm` (default 1413.0 µS/cm) and stabilized raw ADC voltage, with backend computing $K_{\text{cell}}$ deterministically.
  5. *Wire Contract & Single Fixture Source of Truth:* Standardizes all MQTT timestamps to integer Unix epoch seconds (`ts`). Telemetry reports `water_temp_c = 27.0` baseline constant in Phase 1. Contract establishes single canonical JSON schema fixtures (`schemas/*.json`) parsed and validated by both backend pytest (Pydantic v2) and firmware PlatformIO native host tests. Removes `ts` from LWT payload (disconnection time stamped on backend receipt).
  6. *Authentication & Event-Driven Push:* Drops `?token=` from WebSocket URLs (Nginx injects upstream `Authorization: Bearer` for Gazebo TV; Kiosk and PWA use session cookies). Restricts `POST /auth/elevate` strictly to loopback (`127.0.0.1:8080`) recording `elevated_by` in `audit_logs`. Replaces redundant backend 1.0 Hz WebSocket push loop with event-driven broadcasting upon MQTT message receipt and FSM state changes plus connection hydration.
  7. *Phase 1 Scoping & Cleanups:* Restricts `POST /batches` to start-now only (scheduling managed exclusively via `/schedules`). Rejects `tank_pair_id != 1` with HTTP 422 until additional pairs are plumbed.

- **D-051 (Testing Pyramid Architecture, Dual Dosing Constants, Command TTL & Quality Gates):**
  1. *Dual Calibrated Dosing Constants & Golden Vectors:* Retains two distinct physical constants: $K_{\text{feedforward}} = 94.68\text{ ppm}\cdot\text{L}/\text{mL}$ for initial clean-water bulk dosing ($V_{\text{fert}} = (\text{TDS}_{\text{target}} - \text{TDS}_{\text{base}}) \times 140.0 / 94.68 \approx 1695\text{ mL}$ at 104 ppm base $\to$ 1250 ppm target) and $K_{\text{yield}} = 107.0\text{ ppm}\cdot\text{L}/\text{mL}$ for post-dilution deficit top-up ($V_{\text{topup}} = (\text{TDS}_{\text{target}} - \text{TDS}_{\text{meas}}) \times 140.0 / 107.0$). All test fixtures are pinned with realistic physical values.
  2. *Deficit Top-Up Limit & Starvation Trip:* Calculated deficit dosing exceeding the 300 mL mechanical cap ($\Delta\text{TDS} > 229.3\text{ ppm}$) immediately trips `STARVATION_SUSPECTED` and halts the batch without energizing Relay 2, preventing dry peristaltic wear and fluid waste.
  3. *IL-06 Radar Watchdog Gated Recovery:* Resolves cross-file recovery ambiguity by choosing NVS latching. Once FMCW radar UART frames resume stably for $\ge 3.0\text{ s}$, the fault requires an explicit operator `RESET_FAULT` command to clear, but does NOT require draining Drum 2 to $\le 8.0\text{ L}$.
  4. *Dual-Layer Command TTL & Replay Protection:* Eliminates stale queued command execution hazards upon broker reconnection via dual-layer expiry: Mosquitto enforces `message_expiry_interval = 30`, and ESP32 Core 0 inspects command timestamps against SNTP time, rejecting commands older than 30 seconds ($|t_{\text{now}} - t_{\text{cmd}}| > 30\text{ s}$) with `COMMAND_EXPIRED`.
  5. *Dynamic TDS Tolerance Gate Band:* The tolerance gate band is evaluated dynamically against `recipe.tolerance_band_ppm` (default $\pm 50\text{ ppm}$), bounded by firmware safety clamping within $[10, 100\text{ ppm}]$.
